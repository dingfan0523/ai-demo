# Redis 缓存模式、生产坑位与一致性

## 缓存的核心问题

缓存不是“把数据放 Redis”这么简单。生产缓存设计至少要回答：

- 数据源是谁？
- 缓存 miss 怎么加载？
- 缓存何时过期？
- 数据库更新后缓存怎么处理？
- 击穿、穿透、雪崩如何防？
- 大 key、热 key 怎么发现和治理？
- Redis 故障时业务如何降级？
- 缓存不一致时业务能否接受？

## Cache Aside

最常见模式：

1. 查询缓存。
2. 命中直接返回。
3. 未命中查数据库。
4. 写入缓存并设置 TTL。

更新时通常：

1. 更新数据库。
2. 删除缓存。

为什么是删除缓存而不是更新缓存：

- 更新缓存容易和并发读写交错产生旧值覆盖新值。
- 很多缓存值由复杂聚合生成，更新成本高。
- 删除后让下一次读按数据库重建，语义更简单。

隐藏坑：

- 删除缓存失败会导致旧缓存继续存在。
- 删除缓存后并发读可能把旧数据库值写回缓存。
- 热点 key 删除后可能发生击穿。

## Read Through、Write Through、Write Behind

Read Through：

- 应用读缓存，由缓存层负责加载数据。
- Java 里常见于 Spring Cache 抽象。

Write Through：

- 写请求同时写缓存和数据源，缓存层参与写路径。
- 一致性比 Cache Aside 可控，但写延迟更高。

Write Behind：

- 先写缓存，异步刷数据库。
- 吞吐高，但丢数据和顺序风险高。
- 适合可补偿、可重放、不强一致的场景。

## 缓存穿透

缓存穿透是请求查询不存在的数据，缓存 miss 后每次都打数据库。

治理：

- 缓存空值，设置较短 TTL。
- 参数校验，非法 id 直接拒绝。
- Bloom Filter 判断可能存在，不存在则直接返回。
- 风控限流，拦截恶意扫描。

隐藏坑：

- 空值缓存会占内存，TTL 不宜过长。
- Bloom Filter 有误判，不会漏判。误判会放行到数据库，但不存在被误判为存在是可接受成本。
- Bloom Filter 删除困难，数据删除场景要考虑 Cuckoo Filter 或重建。

## 缓存击穿

缓存击穿是某个热点 key 过期，大量请求同时 miss 打到数据库。

治理：

- 互斥锁重建：只有一个线程查库并回填，其余等待或返回旧值。
- 逻辑过期：缓存值里存过期时间，到期后后台异步刷新，前台先返回旧值。
- 热点 key 不设置物理过期，由后台任务刷新。
- 本地缓存 + Redis 二级缓存。

隐藏坑：

- 互斥锁等待会增加尾延迟，需要超时和降级。
- 逻辑过期会返回旧数据，要业务接受。
- 热点永不过期需要补偿任务和人工刷新能力。

## 缓存雪崩

缓存雪崩是大量 key 同时失效或 Redis 整体不可用，流量集中打到数据库。

治理：

- TTL 加随机抖动。
- 分批预热。
- 多级缓存。
- 限流、熔断、降级。
- Redis 高可用部署。
- 数据库保护阈值。

隐藏坑：

- 只加 Redis 集群不能解决大量 key 同时过期。
- 只靠加机器不能解决数据库被瞬时流量打穿。
- 预热任务失败也可能制造雪崩。

## 缓存与数据库一致性

经典更新顺序：

- 先更新数据库，再删除缓存。

为什么不推荐先删缓存再更新数据库：

- 线程 A 删除缓存。
- 线程 B 查询缓存 miss，查到旧数据库值，写回缓存。
- 线程 A 更新数据库。
- 缓存中保留旧值直到 TTL 过期。

先更新数据库再删除缓存仍有问题：

- 数据库更新成功，删除缓存失败。
- 删除缓存后，另一个并发读可能在极端时序下写入旧值。

缓解：

- 删除失败重试，写入消息队列或本地 outbox。
- 设置合理 TTL，让不一致有上限。
- 延迟双删：更新 DB 后删缓存，延迟一小段时间再删一次。
- 通过 binlog/CDC 异步失效缓存。
- 强一致场景不要只靠缓存维护正确性。

## 延迟双删

流程：

1. 更新数据库。
2. 删除缓存。
3. 延迟一段时间。
4. 再删除缓存。

适合：

- 读写并发较高。
- 可以接受短时间不一致。

难点：

- 延迟时间不好定，要大于典型读请求查库加写缓存时间。
- 延迟任务要可靠。
- 仍然不是强一致保证。

## TTL 设计

原则：

- 所有缓存 key 尽量设置 TTL，避免永久脏数据。
- TTL 加随机抖动，例如基础 30 分钟加随机 0 到 5 分钟。
- 热点 key 可用逻辑过期替代物理过期。
- 空值缓存 TTL 短于正常数据。
- 不同业务域分层设置 TTL。

常见 TTL：

- 用户基础资料：几分钟到几十分钟。
- 商品详情：几十秒到几分钟，视价格库存敏感度而定。
- 配置项：较长 TTL + 主动刷新。
- 验证码、token：严格业务有效期。
- 排行榜：短 TTL 或异步刷新。

## 大 key 生产事故

典型表现：

- Redis CPU 飙高。
- 慢查询出现 `HGETALL`、`SMEMBERS`、`LRANGE 0 -1`。
- 网络出流量暴涨。
- 删除某个 key 后延迟尖刺。
- Cluster 迁移某个 slot 极慢。

治理：

- 设计阶段限制集合大小。
- 分页和分片。
- 使用 `SCAN` 系列。
- 使用 `UNLINK` 异步删除。
- 建立大 key 巡检和报警。

## 热 key 生产事故

典型表现：

- Cluster 某个节点 CPU 或带宽远高于其他节点。
- 某个商品、活动、配置 key QPS 极高。
- key 过期瞬间数据库被打爆。

治理：

- 本地缓存。
- 热 key 分片。
- 请求合并。
- 互斥重建。
- 限流降级。
- 提前预热。

## 缓存预热

适合：

- 活动页。
- 首页推荐。
- 榜单。
- 商品详情。

注意：

- 预热要限速，避免启动时打爆数据库。
- 预热失败要告警。
- 预热数据要和数据库版本一致。
- 预热 key TTL 要加抖动。

## 缓存降级

Redis 不可用时的策略：

- 返回本地缓存旧值。
- 返回默认值。
- 关闭非核心功能。
- 限制接口访问。
- 直接读数据库但限流。
- 对写路径使用队列缓冲或快速失败。

面试表达：

- 缓存是性能组件，不应让 Redis 故障拖垮主业务。
- 降级策略要按业务重要性区分，而不是所有接口统一失败。

## 分布式锁场景边界

适合：

- 防止重复构建热点缓存。
- 防止定时任务多实例重复执行。
- 降低并发下外部接口调用次数。

不适合单独承担：

- 金额唯一扣减。
- 库存最终正确性。
- 订单状态机强一致。

正确原则：

- Redis 锁用于效率，数据库唯一约束、乐观锁、事务用于正确性兜底。
